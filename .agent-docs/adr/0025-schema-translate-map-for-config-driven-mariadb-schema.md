# Make the MariaDB schema config-driven via `schema_translate_map`, not per-model edits

Every SQLAlchemy model across `libs/common`, `apps/octopus-app`, and `apps/hive-app` hardcodes `schema="octopus"` — 11 occurrences in `__table_args__` across the three packages' `model.py` files, plus 2 more in `apps/octopus-app/octopus_app/data/mysql/client.py`'s standalone `weather_observation_table`/`weather_forecast_table` Core `Table` objects. `libs/common/common/mariadb/client.py`'s `SessionBuilder` already builds its connection URI from `settings.database`, but that only selects the connection's default database — it does nothing to the literal `"octopus"` schema baked into each `Table`'s `__table_args__`, which SQLAlchemy uses to fully qualify every compiled query regardless of the connection's default database. Discovered during Copilot review of [#548](https://github.com/mholubinka1/home-monitoring/pull/548) ([#549](https://github.com/mholubinka1/home-monitoring/issues/549)): the (since retired) rename runbook's "update `config.yml`'s `mariadb.database`" step does not actually retarget the apps — they'd keep reading/writing `octopus.*` after data moves to `home_monitoring`.

The decision: leave every `schema="octopus"` literal in place, permanently, and instead set `engine.execution_options(schema_translate_map={"octopus": settings.database})` once, in `SessionBuilder.__init__`. SQLAlchemy rewrites every compiled statement — ORM queries, raw Core `Table` queries, and Schema Sync's `create_all`/`ALTER TABLE`/`CREATE INDEX` DDL — to target `settings.database` instead of the literal source key, at execution time, on every connection drawn from that engine. `"octopus"` becomes a fixed placeholder token, not a database name.

This is why a future reader will see `schema="octopus"` still hardcoded in 13 places even after the Pi's database is renamed to `home_monitoring` — that is intentional, not a missed rename. The one change point (`SessionBuilder`) is a smaller, lower-risk surface than 13 call sites across three packages, and the pattern is already trusted in this codebase: `libs/common/tests/conftest.py`'s `mariadb_client` fixture already uses `schema_translate_map={"octopus": None}` to run these same models against SQLite.

One piece of fallout from this change touches tests, even though production code has exactly one change site: `SessionBuilder` now always derives and applies its own `schema_translate_map` from `settings.database`, so a fixture still passing `database="octopus"` would get a second, conflicting `{"octopus": "octopus"}` map layered on top — meaningless against SQLite, which has no `octopus` database to fall back to. Every SQLite-backed fixture's `settings.database` was changed from `"octopus"` to `"main"` (SQLite's own name for its default/only database) so the two maps agree; this is confined to test files and doesn't change any fixture's actual behavior.

Whether a fixture also needs to keep setting its own `.execution_options(schema_translate_map=...)` on the raw engine, alongside that `settings.database` change, depends on whether it touches the raw engine directly before handing it to `SessionBuilder`: a fixture that pre-populates tables via `metadata.create_all(engine)` or inspects `engine` directly (to seed a "table already exists" starting state, or assert on `inspect(engine)` afterward) must keep its own map, since that code runs against the raw engine, before `SessionBuilder.__init__` ever wraps it — `apps/hive-app/tests/conftest.py`, `apps/octopus-app/tests/conftest.py`, and both packages' `test_schema_sync.py` all do this. A fixture that only ever touches the engine through `MariaDBClientBase`/`SessionBuilder` itself doesn't need its own map at all, since `SessionBuilder`'s own now covers it — `libs/common/tests/conftest.py`'s `mariadb_client` and `test_schema_sync_concurrency.py`'s engines dropped theirs for exactly this reason.

## Considered Options

- **`schema_translate_map` on the engine (chosen)** — one change site, zero edits to any model or Core `Table` declaration, matches SQLAlchemy's documented mechanism for exactly this problem (renameable/multi-tenant schemas), and is already proven to work against this codebase's own models via the existing test fixture.
- **Derive `schema` per-model from `settings.database`** — rejected: `__table_args__` is evaluated once, at class-definition time, before any `MariaDBSettings` object exists (settings aren't read until an app starts up and constructs a client) — forcing settings to be threaded into module import time across three packages purely to compute a dict literal. Also doesn't cover `client.py`'s two standalone Core `Table` objects without extra plumbing, since they aren't part of any model's class body.
- **Runtime check that `octopus-app` and `hive-app`'s configured `database` values agree** — rejected: nothing today enforces the two apps' separate `mariadb.database` config values match, and this issue doesn't change that trust boundary; documented as operator responsibility, consistent with the runbook of the time (since retired).

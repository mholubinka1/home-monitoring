# JSON column for hive-app's heating schedule, breaking the flat-column convention

Every table in this schema (`consumption`, `agreement`, `product_rate`, `agile_forecast`, `cost_forecast`, etc.) uses flat, individually-typed columns — there is no precedent for a JSON column anywhere in this codebase. Designing hive-app's `heating_status` table (see the Wayfinder map, issue #490, and the hive-app-initial-data-scope ticket, issue #494) raised the same question for Hive's now/next/later heating schedule: flat columns per schedule slot (`schedule_next_temp`, `schedule_next_at`, `schedule_later_temp`, `schedule_later_at`, ...) or a single JSON column holding the whole schedule payload.

We chose a JSON column, a deliberate deviation from this repo's established flat-column style. The trade-off: it's opaque to plain SQL (Grafana panels reading it need JSON-path functions rather than a bare column reference) and MariaDB stores `JSON` as a `LONGTEXT` with validation rather than a native type, but it absorbs whatever shape Hive's undocumented schedule payload actually has (see `.agent-docs/research/hive-api-access-approach.md` — there is no official, versioned API contract to design flat columns against) without a Schema Sync change every time that shape shifts.

**Note (2026-10-03):** the schedule as returned by apyhiveapi contains `datetime` values (`Start_DateTime`/`End_DateTime` in each of now/next/later), which a JSON column cannot serialise. They are stored as ISO-8601 strings, converted at the persist boundary (`MariaDBClient.write_heating_status`) so the caller's `HeatingStatus.schedule` is left untouched.

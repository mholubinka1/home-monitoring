# Self-hosted CI triggers on push only; fork PRs get a separate hosted-only workflow

> **Note**: `ci-checks.yml` and `ci-arm64.yml` were later merged into one push-only workflow, `.github/workflows/ci.yml` (spec `chore-ci-speedup`); the push-only trigger decision below is unchanged.
>
> **Note**: everything below about `ci-fork-checks.yml` itself — its introduction, its later composite-action extraction, and the two fork-trust fixes to it — was reversed in [ADR-0013](0013-remove-fork-pr-fallback-workflow.md); the file no longer exists. The push-only trigger redesign for `ci-checks.yml`/`ci-arm64.yml` is unaffected and still stands.

Before this change, both `ci-checks.yml` and `ci-arm64.yml` triggered on `pull_request`, and `ci-arm64.yml` was already self-hosted — meaning a stranger's fork PR against this public repo could execute arbitrary code (via `actions/checkout` of the PR head) on the self-hosted ARM64 runner. We removed `pull_request` from both self-hosted workflows entirely, relying on GitHub matching required status checks to a PR's head commit SHA regardless of which event produced the check run: a `push` to a branch already satisfies that branch's own PR checks, so same-repo PRs lose no coverage. A new `ci-fork-checks.yml`, gated to run only when `head.repo.full_name != github.repository`, covers external contributors on `ubuntu-latest` — GitHub's own sandboxed, ephemeral infrastructure — so the self-hosted runner never receives a `pull_request` event at all.

The alternative — keeping `pull_request` on a hosted job and relying solely on "require approval for outside collaborators" as the safeguard — was rejected because it depends on a manual approval gate as the only backstop rather than making the unsafe trigger structurally impossible on self-hosted infrastructure; defense in depth was preferred given the runner sits on the owner's home network.

`ci-fork-checks.yml`'s lint/type-check steps were later extracted into a local composite action (`.github/actions/code-quality-checks`) shared with `ci-checks.yml`, to avoid duplicating ~70 lines of steps. A Copilot PR review then caught a check-integrity gap this introduced: referencing a local composite action by `uses: ./...` after checking out the fork's head SHA lets the fork rewrite the action's own definition to fake a passing result — GitHub only protects the top-level workflow YAML from fork tampering on `pull_request` events, not locally-referenced actions resolved from the checkout. This is distinct from the runner-exposure problem the rest of this ADR addresses (`ci-fork-checks.yml` never touches the self-hosted runner either way); left unfixed, it would have let a malicious fork PR show a fraudulent green check on `ubuntu-latest`, risking a merge that then reaches the self-hosted runner via the push-triggered workflows afterwards. Fixed by checking out the composite action's directory a second time, sparse and separately, from `github.event.pull_request.base.sha` (the trusted target branch) into `.trusted-config/`, and pointing `uses:` there instead of at the fork-controlled copy. A second Copilot review caught the same class of gap one file over: `.github/coverage-baseline.txt`, read from the fork's own checkout to set `--cov-fail-under`, let a fork PR lower its own coverage bar to force a green check. Folded into the same trusted checkout rather than adding a third one, since it's the same trust boundary.

**Known residual gap, accepted rather than fixed**: `pyproject.toml` itself — ruff's `ignore` list, coverage's `omit` list, pylint/mypy/bandit config — is still read from the fork's own checkout, so a sufficiently deliberate fork PR could still widen those to silence findings the trusted-config fixes above don't cover. Fully closing this would mean hardcoding every tool's flags on the command line instead of letting them read `pyproject.toml`, which is a real toolchain redesign with its own trade-offs (legitimate contributors lose the normal way to justify a lint exception), not a small extension of the trusted-checkout pattern — out of scope for this change. Accepted because it doesn't reopen the actual boundary this ADR is about: `ci-fork-checks.yml` never touches the self-hosted runner regardless of whether its check result can be gamed, and a fraudulent green check still can't bypass the CODEOWNERS-required human review before merge (see the CODEOWNERS ruleset added alongside this work) — the human reviewer, not the automated check, is the actual backstop against fork-controlled code reaching the self-hosted runner post-merge.

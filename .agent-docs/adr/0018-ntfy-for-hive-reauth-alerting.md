# ntfy.sh as hive-app's re-auth alert channel

Every existing job in this repo signals failure passively, through `job_run` rows a Grafana staleness panel surfaces on demand — nobody is notified proactively; you have to look at the dashboard. hive-app's Hive client introduces one failure mode that pattern doesn't fit: if Cognito forgets its remembered device, recovery needs a live SMS 2FA code, something a headless service cannot supply itself (see `.agent-docs/research/hive-api-access-approach.md`). A dashboard staleness panel that nobody's looking at leaves the heating client silently dead until someone happens to check.

"Cognito forgets its remembered device" is the canonical case, but the alert covers every apyhiveapi failure that likewise needs a live re-login (see `_REAUTH_REQUIRED_EXCEPTIONS` in `hive_client.py`), and fires at container startup as well as from the heating poll, de-duplicated across both by a single shared `ReauthAlert`.

We chose ntfy.sh — a single HTTP POST to a topic URL, no account/SMTP setup — as the first proactive/push alert channel this repo has, scoped narrowly to only this one failure case (not a general-purpose alerting mechanism for every job failure; those stay on the existing `job_run`/dashboard pattern). This is a real precedent: it's the first time this codebase reaches outside its own dashboard to push a notification, and future features reaching for "alert me about X" should reuse this channel rather than each inventing their own.

## Amendment: two notifications, a secret topic, and a way to act on the alert

- **Exactly two notifications**, both about Hive auth: *re-authentication required* and *authentication recovered*. "Recovered" is sent only after a "required" alert was actually delivered, so it never fires on routine successful polls. That "delivered" marker lives in memory only, deliberately: persisting it would be new state for a convenience message, and recovery does not need a restart because every poll re-reads the persisted auth state. A restart between the two notifications simply drops the "recovered" message, which the runbook tells the operator to avoid. Poll failures, startup or config errors, and other apps' failures are still deliberately not notifications.
- **Format.** Title `<app>: <short event>`, plain-sentence body without a timestamp (ntfy adds one), `high` priority when action is needed and `default` for recovery, a status emoji tag plus optionally one context tag, and a `Click` link only when it helps. "Required" links to `deployments/hive-app/REAUTH_RUNBOOK.md` on `main`.
- **Topic.** ntfy.sh topics are public, so the topic is `home-monitoring-hive-auth-ntfy-<guid-no-dashes>` and the GUID is the only secret. The full `ntfy.topic_url` lives only in the Pi's `config.yml`; the repo carries a placeholder and the format.
- **Recovery exists.** The original alert told the operator an SMS login was needed but nothing could perform one. `python -m hive_app.login` (run via `docker exec -it hive-app`) now completes the SMS challenge, registers the device and writes `hive_auth_state.json`; the runbook documents it. This reverses the earlier decision to leave interactive code entry out of scope.

## Amendment: a Hive API timeout is not a re-authentication requirement

Five "re-authentication required" / "authentication recovered" pairs between 2026-10-03 and 2026-10-04 were false alarms. Each followed Hive's cloud API timing out while listing devices: apyhiveapi swallows the timeout, and because hive-app builds a fresh `Hive` per poll there is no cached data, so `startSession` raises its own `HiveReauthRequired` for the empty device list. Authentication was never broken, and the first retry succeeded every time.

- **Observe, don't infer.** apyhiveapi raises the same bare `HiveReauthRequired` for a genuine "device not remembered / SMS challenge" and for the empty-device case, so neither the exception type, its cause nor the device state can separate them. `HiveApiSource` instead records a timeout from the API call during the session; if `startSession` then raises `HiveReauthRequired`, it raises `HiveApiUnavailable` instead.
- **`HiveApiUnavailable` is an ordinary transient failure:** retried with backoff and recorded as a failed `job_run`, never alerted, so no "recovered" notice follows either.
- **Alert timing is unchanged.** Genuine re-authentication failures still alert on first occurrence. Delaying the alert until retries are exhausted was considered and rejected: it would hide the false alarms without fixing their cause, and a long Hive outage would still page for a problem the SMS login cannot fix.
- **Narrow reclassification.** Only apyhiveapi's own `HiveReauthRequired` after a timeout becomes `HiveApiUnavailable`; the other re-login exceptions (invalid device, token refresh failure, 2FA and configuration errors) still alert even if a timeout occurred.
- **Startup too.** Startup login and resume use the same session handling, so a timeout there is also classed as transient; startup authentication already only logs a non-reauth failure, so nothing alerts and the heating poll carries on.
- **Known gap.** A genuine bare `HiveReauthRequired` that coincides with a timeout in the same session would be treated as transient; the next poll, without a timeout, alerts.

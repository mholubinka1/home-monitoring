# File-based storage for hive_auth_state, not MariaDB

`hive_auth_state` holds a Cognito refresh token and the device-remembering triple (`device_group_key`, `device_key`, `device_password`) needed to resume Hive auth without a full interactive login (see ADR context in `.agent-docs/research/hive-api-access-approach.md`). As originally implemented (issue #506, PR #525), this lived as a single-row table in the same shared MariaDB instance every other table in this repo uses — the "existing Schema Sync convention" the issue explicitly asked for.

That convention is wrong for this specific table. Every other table in this schema holds energy/weather data or operational metadata — nothing an attacker could act on directly. `hive_auth_state` is different: possessing its four values is sufficient to impersonate the remembered device and obtain a fresh Hive access token via `REFRESH_TOKEN_AUTH`/`DEVICE_SRP_AUTH`, without the account password or a live SMS code — full read/write access to the Hive account. Storing that in the shared database means every current and future consumer of that instance (Grafana's MySQL data source, any other service #492 eventually points at the same MariaDB) has read access to live Hive credentials as a side effect of sharing a database, not because it needs them. `docker-compose.yml` also maps `3306:3306` to the host, so the instance is reachable from the whole LAN, not just sibling containers.

We chose to persist `hive_auth_state` as a file in hive-app's own `/config` bind mount instead — the same place hive-app's `config.yml` (containing the Hive account password itself) already lives, with the same file-permission trust boundary this repo already relies on for the Octopus API key and MariaDB credentials, which have never been persisted to the database either. This removes the secret from the shared-instance blast radius entirely, at the cost of one more file to include in whatever backs up `/config`.

Column-level encryption (keeping the row in MariaDB, encrypting the sensitive fields app-side) was considered and rejected for this repo's scale: it adds real complexity — key generation, storage, and a rotation story this codebase has nowhere else — while only protecting against "the database is dumped in isolation," not "the host is compromised," which the file-based approach protects against equally well by simply not putting the secret in the multi-consumer service at all. A full secrets manager (Vault, sealed-secrets) was rejected as disproportionate infrastructure for a single-Raspberry-Pi home-lab deployment with no other secrets infrastructure today.

This is a precedent worth reusing: a future table holding a similarly directly-actionable secret (not just data derived from one) should default to file-based storage in that service's own config volume, not the shared MariaDB instance, regardless of what convention the rest of that service's schema follows.
